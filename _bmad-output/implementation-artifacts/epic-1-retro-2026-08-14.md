## Findings

Six seam findings — defects no single story's review could see, because no session ever saw both sides. Each was re-verified against its primary source before being routed here. Story-level findings already recorded in `deferred-work.md` (20 entries) are deliberately not repeated.

### S1 — `production` carries none of the epic *(fix now)*

`git rev-list --left-right --count origin/production...develop` → `0 33`. `git ls-tree -r origin/production | grep workflows` → empty. On that branch `scripts/generate-il2cpp-refs.ps1:97` still reads *"You can now commit these files"* — verified by `git show origin/production:scripts/generate-il2cpp-refs.ps1`.

Two consequences. SPEC's Success signal — *"nothing left in the repo instructs a contributor to commit `game-refs/`"* — is **false on the release branch**; CAP-2 holds on `develop` only. And `ci.yml:13` lists `production` in `push.branches`, but push events resolve workflows from the pushed ref, so that trigger cannot fire there until a release merge carries the file across. The epic was closed `done` on the board (`0366add`) in this state.

**Prevents the next one:** an epic whose success signal says "the repo" should state which branches it means, and closing an epic should check them.

### S2 — `next/feature-framework` was added to the triggers but has no workflow *(defer)*

`41607e3` added it to both trigger lists (`ci.yml:13,15`). That branch contains only `.github/FUNDING.yml`, has zero CI runs, and still carries pre-epic package versions. Its `push` leg is therefore inert. Separately the widening contradicts story 1.1's own frozen task text (`spec-1-1:54` still says *"push on develop/production"*), and it rode in under a commit titled "stop cancelling integration-branch verification" — a real change outside the subject's stated scope.

**Prevents the next one:** a review patch that widens configuration beyond the finding it answers should be its own commit.

### S3 — the red proof is superseded evidence *(fix now)*

`epic-1-context.md:18` sets the bar: *"A green pipeline that never fails on a real defect does not satisfy this."* The only `failure` run in the epic is `31778629722` on `6d20388` — story 1.1's break. Every run after `39e7e61` (the exact pins) and `7ad9b9f` (the props change) is `success`. So the evidence that CI *can* go red describes a tree with unpinned packages and the old `Directory.Build.props`, not the tree that shipped. Neither 1.3 nor 1.4 could have closed this: both carried "Never touch the CI workflow" boundaries, and 1.1's revert had already landed.

This is distinct from the deferred entry about *future* partial-discovery failure; this is about evidence for the tree that actually exists now.
