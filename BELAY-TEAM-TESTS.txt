BELAY TEAM - COOPERATIVE ACCEPTANCE PLAN

Status: experimental source, protocol 27. Full native two-client acceptance is pending.
Both participants must install the exact same build. Automated participants and
the accepted offline local-station reconnection do not establish multiplayer success.

R35 native pilot: matched builds committed three consecutive anchored exchanges
in both directions, with the same person hosting; the final pair remained active
about 407 seconds until an explicit stop. Both PCs displayed rope, but its material
was inconsistent. Only the host applied added fall damage: guest local validation
incorrectly consulted a host-only piton registry. Initial terminal insertion also
failed before an existing-route retry succeeded. The new peer-damage, material,
connection and belayer-input corrections need native retesting; these observations
do not establish full T/V/D/lifecycle acceptance.

Roles and order
  H1: host is belayer; guest is climber.
  H2: host is climber; guest is belayer. Create a new room to exchange the host.
  Run connection and stationary cases first. Proceed to falls only after those pass.
  Use normal Steam accounts with the game available on both computers.
  Record build, game/loader versions, H1/H2, local time and both log files per batch.
  Status per case: PASS, FAIL, NOT RUN, BLOCKED or NOT APPLICABLE. Never infer PASS.

Setup shared by connection cases
  1. Back up the profiles used for testing. Install with the game closed.
  2. Create Multiplayer -> Private -> Belay Team; invite the other participant.
  3. Belayer places fresh station piton S, personally anchors with E, opens L and
     chooses Define station (K while L is open). Remain anchored and stationary.
  4. Climber places a separate healthy backup P within about 2 m of S and personally
     anchors with E. For the first trial, remain about 2 m apart in the same world.
     Later distance cases use the climber's real rope capacity and protection path.
  5. Use L to offer/request and explicitly accept. Close L to operate rope controls.
  6. During initial attachment, keep P attached and remain still. Wait for connection
     confirmation and the native length readback. Do not use the solo Ctrl+F10/F11/F12.
  7. If setup is refused, record the message/time and stop; do not make a fall.
     An empty partner list now reports the rejected state, scene, stale body pose
     or measured distance. Live ghost movement alone does not prove eligibility.
     Proximity uses fresh replicated body positions on both sides, not actor bases.
     Belay Team compares the game's native world identity, not the last streamed
     zone callback. Both builds must use protocol 27; different worlds still refuse.
     R21 carries the climber's capacity in the invitation/acceptance contract;
     R22 adds a role-transaction identity to the fixed-size request/event contracts;
     earlier experimental protocols cannot join this version.
     If E is missing, close L and check your own fresh piton with firm foot holds.
     The panel/BelayAnchor log reports native readiness; it never forces anchoring.

  C04 Reverse invitation: climber requests, anchored belayer accepts; same station
      reference and protection checks apply. Decline/cancel must not start control.
  C05 Station guard: after acceptance/preparation, K/Remove station cannot end
      belay and the belayer's personal-anchor input is locked. L > End belay
      explicitly ends control and unlocks it. Native station failure or identity
      loss must still end the pair; no rollback of queued native operations.
      Attempt the normal wall-grab/climb input as the belayer: the personal

  C06 Near-coincident pitons: use distinct freshly placed pitons where practical.

      Verify personal anchoring completes, the same session stays active and the
      belayer can still brake/feed after the climber releases the personal anchor.
      This native return-to-anchor case is pending; do not infer it from unit tests.

Stationary controls - remain anchored at P
  R01 FREE + Up for 2 seconds: approximately 2 m paid out; release stops explicit
      feed. Check reported slack/reserve, visual change and native length match.
  R02 Down: only slack is taken in, at up to 1 m/s. No upward hauling or shrinking
      below loaded/geometric distance. Releasing the key stops motion.
  R03 Space or F7: latched BRAKED/FREE. Up cannot feed while braked; Down can remove
      slack. Both arrow keys cancel motion. Only the belayer controls this rope.
  R04 L or chat during held motion: motion becomes zero; closing/releasing input
      permits a fresh command. Closing the panel is not acceptance of an invitation.
  R05 Climb above P after releasing personal anchoring: BRAKED blocks outward
      advancement when slack is exhausted, allows retreat, then allows progress
      after FREE/feed. Keep enough clearance to avoid an unintended fall.
  R06 Add one protection while unloaded, first FREE then BRAKED. Expected: native
      split settles, count increases once, budget remains coherent; old held motion
      does not continue across the rebind. Do not remove/reorder a loaded route.
      If native recovery removes an older protection before the active station,
      an unloaded rebind may retain control only when the entire station-to-harness
      holder, segment and physical pin suffix is unchanged. Removing the station
      or a downstream protection, or changing any loaded mapping, is not allowed.
      Native acceptance of this upstream-only recovery is still pending.

  V02 Feed and take in slack while anchored: the belayer's drawing should follow

  V03 Add one unloaded protection, then wait for the route to settle. Confirm

  V04 End belay while personally anchored: the drawing disappears. Reconnect and

      Drawing samples never renew the three-second brake/session lease.

Anchored role exchange - candidate, native acceptance pending
  T01 With the current pair active, the climber places a separate healthy upper
      protection T, waits for rebinding and personally anchors at T. The original
      belayer remains held at S. Open L on the climber: K proposes T as the next
      station. The original belayer accepts with Enter. Both remain still and
      personally anchored throughout preparation. Do not close L or make a fall.
      Expected: both native routes confirm, roles reverse, brake starts closed,
      new rope readback appears, and both personal anchors remain attached.
      Existing-route binding and missing-station insertion must be recorded
      separately; a refused insertion is not a passed role exchange.
      During role preparation, the new station may precede the old protections
      or become the final protection before the harness. Every original protection,
      the same personal backup, both endpoints and physical pins must be retained;
      insertion still needs five observed seconds. Repeat in BOTH directions.
  T02 Cancel/decline the proposal with Backspace, before acceptance and during
      preparation. Expected: original roles and control remain; native queued
      insertions are not rolled back. No automatic release or second role offer.
  T03 After T01 passes, the new climber releases S, climbs toward T while the new
      upper belayer takes in slack with Down, and personally anchors again.
      Expected: slack is collected without hauling; brake and climbing limit work.
      Repeat the role exchange back, then repeat in the other host arrangement.
  T04 Pause/focus/disconnect during a proposal or preparation: L01/L02 still end
      the interaction rather than resume automatically. Check both personal
      anchors, input restoration and fresh-consent requirements afterward.

Falls - only after C/R/T cases pass
  F01 Short fall with BRAKED already set: native catch with coherent slack and no
      excessive upward launch. Record height, slack, damage and piton condition.
  F02 Short fall from FREE, belayer brakes in flight: one catch at current geometry;
      no repeated brake input is needed to keep it latched.
      R15 remains unstable when native holder topology changes after the catch;
      a second recorded stop followed a fall during a pending route update.
      R17 blocks personal rope-grab/ascent input that can split the controlled
      rope into temporary hand segments. Native acceptance of this candidate is
      pending; do not infer stable falls from automated policy tests. Holder-type
      and physical-endpoint diagnostics remain available for any further failure.
  F03 Suspended release/re-brake and take-in: coherent payout/catch; take-in removes
      slack without winching the loaded character. Stop if the earlier gates fail.
  F04 Rope-end knot: later controlled case with suitable clearance and a prepared
      test profile. FREE reaches the native limit; record stop, damage and failure
      outcomes. No assumption of zero injury or guaranteed piton survival.

Shared fall damage - included in this candidate, native acceptance pending
  Enable Debug.BelaySharedDamageExperiment on both clients (the cooperative test
  installer does this). Keep the existing damage balance and one-second catch
  observation. No solo Ctrl+F9/F10/F11/F12 exercise is needed in multiplayer.
  D01 After F01, remain suspended for at least one second plus network delivery.
      Expected: one measured catch and host-approved climber addition at most once;
      native Fall HP loss is credited against the height-attenuated curve. The HUD
      and BelayDamage logs report requested and actually observed local HP changes.
      Effort/exhaustion drain must not count as native Fall damage.
  D02 The belayer receives 30% of the climber's actual completed native-plus-added
      fall HP loss fraction, scaled to the belayer's own maximum HP. With both at
      100 maximum HP, a 20 HP observed climber fall requests 6 HP from the belayer.
      The native damage path can reduce that result through game protections;
      zero native HP loss is a valid result when documented in the logs. There is
      no forced belayer ragdoll, direct HP overwrite or duplicate damage retry.
  D03 Repeat a short catch from FREE then brake, and later vary slack and height.
      Small falls must retain the existing height attenuation. Wait for the damage
      result before grabbing a piton or requesting a role exchange. An invalidated
      observation must report an incomplete result rather than apply stale damage.
  D04 Repeat D01-D03 after a successful anchored role exchange and with the other
      person creating the room. Damage must follow the current roles, not host
      identity. Each catch has a distinct identity; old approvals cannot affect
      the new pair. A pending decision briefly blocks a new exchange.
  D05 While personally anchored, use L > End belay and reconnect. No old damage
      decision may apply to the new session. Pause, focus loss, cutscene and
      disconnect still end the pair as in L01/L02; returning does not resume it.

Interruption and persistence - start anchored, without a fall
  L01 Pause menu, Alt+Tab/focus loss and an available natural cutscene, each for
      belayer and climber and during preparation. Expected: session ends, motion
      stops, an already queued native operation may finish. Returning does not
      automatically restart; revalidate anchors and send a fresh invitation.
      If no natural cutscene is available, mark that part NOT RUN.
  L02 Disconnect each participant through the normal UI while the climber remains
      anchored at P. Expected: no new commands, no stale control after rejoining.
      Check personal protection before continuing. Do not use firewall changes.
  L03 End belay through L, then remove the station. Personal anchoring stays attached.
      A new invitation is required; stale prior-session messages cannot restart it.
  L04 Save/reload and duplicate-piton investigation, after the core cases and a
      profile backup: record counts/positions before save, after reload, after
      rejoining and after leaving. Look for repeated copies/inventory changes.
      This build does not repair old saves or delete duplicates by position.
      Position-only rebound identities refuse station binding; use fresh pitons.
  L05 Stable run longer than 5 minutes with fresh partner input: no two-minute
      diagnostic cutoff. Record stutters, crashes and any growth of log volume.
  L06 Repeat C03/R01-R06/F01-F03 in H2. Record natural latency and host/client roles;
      passing only one host arrangement is partial acceptance.

Later scenarios / not implemented acceptance
  N01 Start a NEW upper-station belay session without falling first. Validate native
      station order and take-in before follower falls. This is not protected role
      transfer within the existing pair; record a refused route as a failed case.
  N02 Loaded or seamless role transfer is not implemented. T01-T04 test an
      explicitly consented, stationary exchange with both personal anchors held.
  N03 Preserve pair and resume after cutscene/pause: BLOCKED; first pilot ends the
      interaction by design. A future resume must revalidate route/anchors and input.
  N04 A forced belayer ragdoll is not implemented. Shared damage is included and
      tested by D01-D05 above; both native health protections and piton failure
      handling remain in effect.
  N05 Third-player injection and multi-pair behavior: optional later manual cases;
      one pair is supported. Automated authorization checks do not replace native tests.

Stop and evidence
  If connection/readback fails, remain personally anchored and report the message,
  case id, H1/H2 and time. Do not advance into fall cases to compensate for failure.
  Finish the current round before switching windows: losing focus ends the session.
  Collect both MelonLoader/Latest.log files before relaunch (the log is replaced).
  Review/redact shared diagnostic bundles; do not send saves or game DLLs.
  A local PASS means only its exact scenario/build. Multiplayer, damage/failure,
  lifecycle and performance acceptance must be recorded separately.
